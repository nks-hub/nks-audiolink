# Alternatives and development priorities

Checked against primary upstream documentation on **2026-10-23**. This is a comparison of documented capabilities and setup, not a benchmark or a claim that AudioLink has lower latency, better sound or more reliable recovery than another project. The alternatives were not installed or tested during this review.

AudioLink's current scope is one Windows source feeding one Linux ALSA output on a trusted LAN or VPN. Playback-device loopback uses WASAPI without installing a virtual audio driver; optional virtual-device routing requires a separately installed VB-CABLE. Transport is fixed at 48 kHz, signed 16-bit stereo PCM over UDP, with 5 ms frames. The server accepts one active session. See [Windows setup](WINDOWS.md), [Linux setup](INSTALL.md) and the [wire protocol](PROTOCOL.md).

Additional references have led to audio-path changes: SonoBus's automatic receive buffering and live audio controls, OBS's application-specific capture, and Snapcast's receiver-management workflow. AudioLink uses its own predictive buffer/limiter policies and NAudio's existing MIT-licensed native capture wrapper; no competitor implementation was copied. Its explicit single-session takeover is an AudioLink workflow choice, not a claim of Snapcast feature parity.

## Choosing an architecture

| Project | Capture, routing and formats | Receiver model and practical fit |
|---|---|---|
| **AudioLink** | WASAPI playback loopback, recording input or optional VB-CABLE; fixed stereo PCM format above | One Windows sender and one Linux ALSA receiver. Fits a PC feeding an existing sound card without a Linux desktop/audio server. |
| **[Scream](https://github.com/duncanthrax/scream#readme)** | Windows virtual sound-device driver; configurable PCM sample rate, width and channel layout; UDP multicast or optional unicast | Multiple receivers can subscribe to multicast. Unix receivers support ALSA, PulseAudio and JACK. Consider it when a virtual network sound device or multicast is the main requirement. |
| **[Snapcast](https://github.com/snapcast/snapcast#readme)** | Server ingests sources such as pipes, ALSA or a process; PCM, FLAC, Vorbis and Opus codecs over TCP | Time-synchronized clients and groups support multiroom playback. Windows audio must be routed into a supported server source; this is a different setup from selecting an AudioLink loopback device. |
| **[VBAN / Voicemeeter](https://vb-audio.com/Voicemeeter/vban.htm)** | Public UDP protocol; Voicemeeter routes named incoming/outgoing streams with multiple PCM rates and up to eight channels per stream | Fits mixer workflows and VBAN interoperability. The protocol itself has no shared clock/synchronization procedure; receiving the same broadcast is not proof of synchronized multiroom playback. See the [protocol specification](https://vb-audio.com/Voicemeeter/VBANProtocol_Specifications.pdf). |
| **[SonoBus](https://sonobus.net/)** | Audio-device input or DAW plugin; uncompressed 16/24/32-bit PCM or Opus | Peer-to-peer groups on LAN or Internet, with mixing and recording. Relevant when bidirectional collaboration or several participants matter more than a dedicated Windows-to-ALSA service. |

These are different wire protocols. AudioLink cannot currently send to their receivers or accept their streams.

[OBS application audio capture](https://obsproject.com/kb/application-audio-capture-guide) is a focused capture reference rather than a replacement Windows-to-ALSA transport. Its useful workflow is selecting one application instead of the entire desktop. AudioLink now offers that source mode, including the selected process's children. Microsoft documents the [native process-loopback API](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/) with an original build 20348 requirement; OBS documents updated Windows 10 2004+ support. AudioLink checks actual activation and was exercised successfully on build 19045, while reporting unsupported capability explicitly on systems that lack it.

## Setup, diagnostics and recovery

| Project | Documented operating model | Consequence for this review |
|---|---|---|
| **AudioLink** | Portable Windows app/CLI; Linux systemd service and JSON configuration. Desktop statistics, activity history, stereo RMS/peak/clipping meters and optional read-only HTTP dashboard/API with history. HTTP is disabled by default; suggested TCP port **7356** is separate from UDP **7355**. | Inspect sender and sink levels together, then buffer/RTT/error counts and native ALSA logs. Reconnection and output recovery have their own regression and hardware evidence below. |
| **[Scream](https://github.com/duncanthrax/scream#readme)** | Driver installation needs administrator access; upstream documents Windows driver-signing constraints. Format is configured through Windows sound-device properties; unicast uses registry settings. A Wireshark dissector supports packet inspection. | Installation on the intended Windows version needs its own check. This review did not exercise Scream's restart, sleep or driver lifecycle. |
| **[Snapcast](https://github.com/snapcast/snapcast#control)** | Server configuration defines streams; Snapweb and a JSON-RPC API manage clients, volume and groups. | Its web interface includes control, while AudioLink's HTTP interface only observes. Multiroom timing and recovery would need a separate comparative test. |
| **[Voicemeeter](https://vb-audio.com/Voicemeeter/index.htm)** | Mixer plus virtual audio devices; its installer requires administrative setup and a restart. VBAN configuration selects named streams, destinations and routing. | Account for the mixer and driver configuration, not just UDP packet support. No VBAN implementation was tested for dropout or suspend recovery here. |
| **[SonoBus](https://sonobus.net/sonobus_userguide.html)** | Per-peer levels, latency/jitter information, and manual or automatic jitter-buffer adjustment. Windows documentation recommends an appropriate ASIO driver. | Useful reference for exposing the buffer-versus-dropout tradeoff. Its Internet/group recovery behavior was not benchmarked here. |

AudioLink's ten-minute hardware run passed after fixing skipped output deadlines: **600.002 seconds**, zero jitter counters and native recovery/error events, one unchanged process/session/ALSA trigger and **1.260% of one CPU core**. Actual S3 resume recovered automatically in **11.72 seconds** after the Windows wake event. Controlled ten-second UDP interruption, server restart and immediate busy rejection were also exercised. These are observations on the reviewed setup, not universal guarantees. Earlier failed/interrupted runs remain in [VALIDATION.md](VALIDATION.md#additional-live-checks-2026-10-23).

## Latency and licensing limits

Buffer size, peer synchronization accuracy and physical input-to-speaker delay are different measurements. Snapcast's upstream synchronization figures describe alignment between clients; they do not establish total physical latency. SonoBus documents how buffering trades delay for resistance to jitter. Neither figure can be ranked against AudioLink's summed UI estimate without the same devices, source, network, settings and measurement endpoints. [Snapcast timing](https://github.com/snapcast/snapcast#how-does-it-work), [SonoBus latency guide](https://sonobus.net/sonobus_userguide.html#about-latency).

AudioLink's physical end-to-end latency remains unmeasured. The timestamped LAN-to-WAV test excludes capture and physical playback; the UI estimate includes known software queues but cannot measure downstream receiver delay. The pending flash/click assessment is separate from those numbers. See [measurement scope](VALIDATION.md#latency-and-cpu).
